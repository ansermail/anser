# QQ 实时收取延迟核查

2026-10-20，main，基线 `9398046`；当前正式版本 0.1.23。修正已进入 0.1.24 发布，真实 IDLE 主动推送已复验。

## 当前状态：收件箱改由监听连接独占（2026-10-20，真实推送已复验，随 0.1.24 发布）

按 Mac Mail / Thunderbird 的每账号一条 INBOX 会话模型修正：此前推送触发收取、五分钟兜底和手动检查都会新开短连接 EXAMINE INBOX；0.1.8 有约两秒主动通知的样本时，监听连接可长时间停留在 IDLE。上一阶段两次失败实验（20 分钟持续 IDLE、SELECT）期间仍有这些短连接，无法排除服务端把新邮件通知交给最新 INBOX 会话、短连接关闭后通知丢失。现在 IDLE 连接独占 INBOX，真实 QQ 是否恢复主动推送必须以日志出现“服务器实时通知”验收，不能以分钟级复核代替。

- 目标：让 IDLE 连接成为该账号唯一的 INBOX 会话，观察主动推送是否恢复；不改用户五分钟配置。
- 修改文件：`network.rs`（`watch_session` 接收收取闭包，新增同连接 `sync_inbox_session`；全目录收取跳过被监听账号的 INBOX；周期只读复核后更新基线）；`realtime.rs`（删除 mpsc/jobs/pending/fallback，worker 内联收取；新增监听注册表与单账号代次 `restart_account`）；`lib.rs`（手动收件箱收取后重启该账号监听，`sync_scope` 复用，新增同连接收件诊断日志）；`idle.rs`（删除不再使用的主动通知注册，只观察目录变化）。
- 连接内顺序：能力核对 → 只读打开 INBOX → 连接后补查 → 每分钟 EXAMINE 复核 → IDLE（等待上限取复核、定时补查与 29 分钟保活三者最小值）。推送或复核发现变化后在 DONE 回执之后用同一会话下载；下载结束后再复核一次，下载期间到达的邮件会立即再收一轮，完整下载后重新计算定时补查。
- 竞态保护：监听在拨号前登记自己占用 INBOX，全目录收取除构建目录列表时过滤外，选中前再核对一次，因此启动或定时收取期间新出现的监听不会被后续短会话抢走最新 INBOX 选择。
- 本机预览：新构建启动后 QQ 与企业邮均记录“实时收取已连接（IMAP IDLE）”，随后在同一连接上完成“监听连接后补查”并成功；两个监听各保持一条到本地代理 7890 的已建立连接。此记录只证明新模型已运行，**不证明主动推送已恢复**。
- 边界：监听连接只收取收件箱，不代替其他目录的历史收取、不写标记、不发信；复核失败丢弃整个会话，不复用失步连接；后台全目录收取跳过被监听 INBOX，避免再产生第二个收件箱会话。
- 验证：`cargo test --manifest-path src-tauri/Cargo.toml --lib` 391 通过/3 既有忽略（network 50 项，含 DONE 后用同一连接下载、复核被拒即丢弃会话两项新回归）；`cargo fmt -- --check`、`git diff --check` 通过。
- 未完成：真实 QQ 联调（需要一封企业邮 → QQ 测试邮件，观察是否由“服务器实时通知”触发）；外部代理线路仍未隔离；其他服务商、睡眠/弱网未验证；未提交/未发布。开发预览继续用 `npm run desktop`，重编译后等 Tauri 输出 `Running` 且进程由启动器管理后再操作原生界面。

### 主流方案与当前结论

- 通用桌面 IMAP：保持 IDLE 长连接，由服务器响应唤醒增量收取；重发 IDLE 的保活周期与收件轮询周期不同。标准建议至少每 29 分钟重发，期间仍可即时通知。[RFC 2177](https://www.rfc-editor.org/rfc/rfc2177.html)
- Gmail 的官方 API 推送通过 `watch` + Cloud Pub/Sub，通知后按 history 增量同步；Outlook 可使用 Microsoft Graph change notifications，通常接入通知接收服务。[Gmail](https://developers.google.com/workspace/gmail/api/guides/push)、[Microsoft Graph](https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview)
- 雁信仍以 IDLE 为主路径，每分钟目录复核是新增防漏检措施，不能认定为恢复即时推送。此前“原因已定位”的说法过强，现明确收窄为上述协议观测证据；要进一步隔离实际外部代理/QQ 服务端，需要在不擅自绕过全局代理的前提下做线路对照。
- 独立第三方 QQ 客户端作者也记录了 IDLE 通知不稳定；它只能支持该现象并非本项目独有的可能性，不能替代本次线路的根因证据。[qqmail-cli 作者说明](https://github.com/situker/qqmail-cli/blob/main/README.md#什么时候不该用它)

用户完成系统授权后，第二轮真实 QQ 联调由新增的 EXAMINE 目录复核发现变化，未等到下一次五分钟补查。NOOP 本轮没有触发变化，服务器主动 IDLE 通知也未触发；因此确认仅靠原先的 NOOP/数量通知存在实际漏检覆盖缺口，重新读取只读目录状态可发现新邮件。该结论针对本轮可复现的真实样本；14:30–14:45 历史响应没有留存，不追溯断言其唯一服务端原因。

QQ 的 `20261020-IDLE-FIX-02` 测试正文已在原生阅读页目视核对；清理临时诊断后开发预览继续运行。用户原五分钟配置未改，正式安装目录未覆盖。

## 修改与协议边界

- `src-tauri/src/network.rs`：60 秒 IDLE 周期结束后，NOOP 检查存活，再 EXAMINE INBOX 刷新只读目录快照；二者共用原 45 秒绝对响应期限。初次打开同样核对完整 EXISTS。失败丢弃连接并沿用退避；停止时启动下一轮 IDLE 的竞态按主动停止处理。
- `src-tauri/src/idle.rs`：复用现有 IMAP 解析器观察 EXISTS/EXPUNGE/UIDNEXT/UIDVALIDITY，重复值与初次建立基线不触发，编号边界变化即使总数相同也触发。回调仍在活动锁外、tagged 确认前排队；NOOP 的 ProbeChanged 和 EXAMINE 的 RefreshChanged 分开记录，均可让出历史 FETCH。
- 监听不 FETCH 正文、不写标记、不发送邮件；保持现有身份、隔离、来源及原件保护。五分钟用户配置未缩短，60 秒只读复核不冒充即时推送保证。
- 依据 [RFC 3501 EXAMINE](https://www.rfc-editor.org/rfc/rfc3501.html#section-6.3.2) 和 [IDLE](https://www.rfc-editor.org/rfc/rfc2177.html)。
