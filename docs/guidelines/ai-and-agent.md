# AI 功能与 Agent 开发协作规范

本文件涵盖两类规则：（1）应用内 AI 功能（写信 AI 助手、双语翻译、摘要、工作报告及通用模型配置）的协议与隐私边界；（2）AI Agent 在本仓库开展日常研发、维护记录与操作开发预览的协作规范。

---

## 一、应用内 AI 功能规范

### 1. 模型配置、凭据与通用兼容边界

- **通用 OpenAI 兼容**：邮件翻译、摘要、写信修复与 AI 工作报告共用同一套全局 OpenAI 兼容配置与加密凭据，服务专用参数仅发给精确匹配的官方接口，不硬绑定 DeepSeek 或单一模型；模型 ID 支持手填或通过用户主动获取 `/models` 列表选择。
- **凭据与安全隔离**：配置与 API Key 分离，Key 仅存本地加密凭据库；更换服务地址不得沿用旧 Key，模型发现不得将旧服务 Key 发往新地址，也不写配置或发补全正文。远程请求统一走全局代理并校验 TLS，HTTP 仅允许本机模型，禁止 HTTP 重定向转交认证头。演示模式禁止连接真实模型或保存 Key。
- **保存前实测验证**：模型配置保存前必须使用当前候选配置与候选密钥请求固定虚构测试文本（绕过缓存读写，不能用历史译文冒充连接成功）；未保存改动时不测试旧配置；验证失败不写入配置、凭据或 revision，并保留表单内容供修改。

### 2. 写信「AI 助手」与写信修复

- **UI 与交互边界**：写信「AI 助手」完全基于 shadcn/ui 与 `src/components/ai-elements/`（参考 shadcn AI Elements 组合 `Conversation`、`Message`、`ChainOfThought`、`Reasoning`、`Plan`、`Suggestions`、`PromptInput`、`Shimmer`），不再依赖第三方 `assistant-ui`。助手与写信框并排、窄窗可从右侧覆盖，不得嵌入正文编辑器；写信工具栏不提供插入本周事项。
- **思考链、思考过程与修改计划**：每轮生成以可折叠思考链展示真实执行步骤（读取可编辑段落范围 → 调用模型并计时 → 校验段落 Diff）；仅当模型返回真实推理文本（`reasoning_content` / `reasoning` / `<think>`）时渲染默认折叠的「模型思考过程」，绝不虚构推理；应用前以可折叠「修改计划」卡片列出逐段改动并由用户显式点击应用或舍弃，整个面板仅保留一套运行中反馈。
- **结构化修复协议**：复用 OpenAI 兼容与官方 DeepSeek 的 JSON 输出路径；修复结果按有界协议校验，可兼容 `text` / `replacement` 字段别名，但未知段落、重复索引、非法换行或非法字符仍须拒绝；后端已知失败须分类映射为双语提示，不得压成通用配置错误。
- **安全应用与撤销**：写信修复仅在用户确认应用后写入当前草稿；Diff 装饰不进入草稿或发件，应用须核对草稿版本并支持独立撤销。

### 3. 大模型双语翻译

- **隐私与数据边界**：仅在用户点击后发送当前单封的可见正文纯文本，不自动发送邮件头、隐藏内容、图片或附件；模型输出按片段 ID 校验并仅写 `Text` 节点，复用净化正文结构，绝不执行模型 HTML；译文及有界缓存独立于 MIME、回复/转发、索引与打印；切换邮件、关闭或配置变化时取消并废弃旧代际结果。
- **提示词与完整性校验**：
  - 请求提供本批次全部准确 ID、条目数与完整 JSON 返回模板，只允许填充 `text`，禁止模型新增片段或重编号；模板只含已验证 ID，邮件正文始终留在不可信 `user` 消息中。
  - 按段落及全部片段 ID 核对完整性：语序调整允许同段部分内联片段为空，整段不得为空；严禁放宽未知/重复/遗漏校验、按数组位置猜配、丢弃漏项掩盖失败或自动重复发起收费请求。前后端使用相同边界，批次尽量不截断同段上下文（超限长段仍守硬限制）；校验协议变化同步缓存版本与回归测试。
- **双语排版规则**（按结构判断，不为发件人/域名/字段特判）：
  - 按钮双语文字必须在原按钮内换行，保留同一安全链接、底色、边框与点击区域（兼容装饰在内层标签与 flex/grid 的按钮），不复制第二个按钮；译文使用紧凑独立行高与零缩进，不复制按钮居中大行高或内边距。
  - 普通 HTML 译文折叠源码缩进（不统一 `pre-wrap` 暴露前导空白），`PRE` 与显式换行按原语义保留（连续 `BR`/保留换行按空行分段，普通 `PRE` 不等同代码）。
  - 纯图片连续组只去默认文字基线缝隙，不改作者显式 `margin/padding/BR`，不对混合正文图标全局清间距。
  - 普通横排链接及带链接页尾按原段落整组内联双语、随宽度自然折行，不逐字段强制换行；与周围重复底色/单边下划线/`inline-block` 本身不算按钮，真实按钮按独立盒子样式/语义识别。
  - 翻译可见性核对祖先样式、裁剪与折叠状态，不因插入译文解除原邮件隐藏边界；隐藏翻译恢复原节点与样式，并在真实 WebKit 中核对 CSSOM 延迟同步（不只依赖 jsdom）。
- **活动日志**：翻译批次与连接测试写入「最近活动」，区分模型请求/本地缓存/未请求、成功/失败/取消或未执行，记录数量与耗时；失败仅写固定分类，严禁记录邮件正文、译文、服务地址、密钥或原始远端错误；演示日志明确标识虚构。

### 4. AI 邮件摘要与 AI 工作报告

- **邮件摘要**：由用户发起并绑定单封；摘要语言跟随翻译偏好中保存的目标语言且参与缓存键（修改目标语言后不得复用旧语言摘要）。使用正文滚动容器外右上角 `12px` 悬浮卡片展示（正文或对话滚动不移动卡片，上下不加内部分割线，长内容卡内滚动）。时间提醒随摘要一次生成，仅在有原文证据与有效日期时展示，通过行内日历图标打开预填事项由用户确认保存。
- **AI 工作报告**：允许用户保存附加提示词指定分组、章节、措辞与 Markdown 格式；附加提示词作为单独可信用户要求发送，仍须保持工作记录不可信数据边界与单一 JSON 文本字段返回约束（后端结构化优先并兼容纯文本报告，但无可用文本字段的纯 JSON 须拒绝）；AI 返回的 Markdown 仅经安全净化后显示，严禁直接插入未净化 HTML；报告输入不包含工时。

## 二、Agent 开发协作规范

### 1. 开工检查与开发记录持续维护

- **开工必查**：先检查 `git status`、当前分支及 `origin`（保留已有未提交工作），再阅读 `docs/DEVELOPMENT_STATUS.md` 顶部当前执行检查点及最新阶段记录；涉及未完工作时读取 `docs/working/features/` 或 `docs/working/releases/` 对应 `*_WORKING.md`，核对分支与代码后从中断处继续。
- **阶段更新**：每个阶段完成、用户调整方向、出现阻塞或交接中断前，更新 `docs/DEVELOPMENT_STATUS.md`（已完成/未完成、实际验证、剩余限制、下一步入口），并同步修正顶部当前检查点与相关清单；旧记录保留日期，禁止让过期的“下一步”与当前入口矛盾。
- **阶段工作点**：未完成的复杂工作须写入阶段工作点（目标、分支/提交、已改文件与设计、未完成步骤、失败/阻塞原因、必要命令与下一步），不得仅依赖聊天上下文、临时日志或运行中 PID。
- **文档同步与归类**：遵循 [docs/README.md](../README.md)——
  - 行为变化同步 `docs/USAGE.md`；架构/协议变化补充 `docs/IMPLEMENTATION.md`；发布变化更新 `docs/UPDATES.md` 与 `docs/releases/v<版本>.md`；`README.md` 保持面向用户的概览与准确发布状态。
  - 功能/走查/排查工作点放 `docs/working/features/`，发版审计工作点放 `docs/working/releases/`，功能设计方案放 `docs/plans/`，截图放 `docs/screenshots/`，不在 `docs/` 根目录平铺临时工作点。
  - 新增长期约束、反复出现的故障根因或重要保护措施，同步维护 `docs/guidelines/` 对应专题规范（核心红线或索引变化同步 `AGENTS.md`）；不在规范文档堆积每轮日志、临时账号状态或一次性测试数据。
- **五阶段分别记录**：**代码完成、自动测试通过、真实场景验收、云端构建、正式发布**必须分别记录。记录测试命令、结果、环境与重要限制；未经执行的检查明确写“未验证”，不得沿用旧结果或将开发预览/Pages 部署成功冒充桌面正式包发布。

### 2. 开发预览与原生操作时序

- 使用 `pnpm desktop` 运行桌面开发应用，优先复用正在运行的开发预览，避免让用户反复安装应用包；禁止绕过现有开发启动器或在签名失败后回退临时签名启动。
- **Rust 重编译等待时序**：Rust 重编译期间严禁绑定或读取原生应用 UI（防止 CUA 在旧实例退出时重启尚未更新的 app bundle）。必须等 Tauri 输出 `Running` 且新应用 PID 的父进程仍是 Tauri 后再开始交互，避免单实例检查拒绝新版、留下旧窗口。
- 实际收取验证期间保持后端代码稳定，不得用重启补收代替实时到达结果。
- 阶段提交应对应实际完成范围，未验收的工作分支不得作为完成代码混入正式发布。

### 3. 文档与营销截图规范

- 官网、宣传视频、README 与文档优先使用演示模式的虚构账号和示例邮件截图，保留 Retina 分辨率并记录来源；图标直接使用应用既有资源，不自行重画；营销媒体仅进入 Pages 构建，不复制进桌面安装包。
- 使用真实邮箱截图前，必须遮盖邮箱地址、姓名、主题、正文、附件名等关键信息并提交用户审核，审核通过后方可加入文档或发布。
