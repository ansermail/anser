# 测试、验收与发布规范

本文件沉淀按改动范围分层检查、大列表测试超时定界、真实收发授权边界、实机验收要点与版本发布流水线约束。流水线细节同步维护于 [docs/UPDATES.md](../UPDATES.md)、[docs/WINDOWS.md](../WINDOWS.md) 与 [docs/HOMEBREW.md](../HOMEBREW.md)。

## 1. 分层检查命令与发布全量门槛

- **按改动范围执行**：
  - **UI / 前端改动**：`pnpm check:ui`、`pnpm check:i18n`（涉及文案）、相关 Vitest 回归（`pnpm test:changed` / `pnpm test:related -- <file>`）、`pnpm build`，并在开发预览核对效果。
  - **Rust / 协议改动**：`cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` 及相关 Rust / IMAP 回归（`pnpm test:rust`、vendored `imap-proto`）。
  - **构建/发布脚本改动**：`pnpm test:desktop`。
  - **官网 / Web 预览改动**：`pnpm build:preview`，核对虚构数据及禁用真实收发/文件读取边界。
  - **打印布局改动**：`pnpm build && pnpm test:mac-print`，并实测系统打印面板分页。
  - **通用提交前门禁**：`pnpm format:check` 与 `git diff --check`。仅修改文档时无需反复构建桌面应用。
- **发布前全量门槛**：遵循 `.github/workflows/ci.yml` 与 [docs/UPDATES.md](../UPDATES.md) 执行全量前端（`pnpm test:ci`）、Rust、桌面脚本、vendored IMAP 解析器（`cargo test --manifest-path src-tauri/vendor/imap-proto/Cargo.toml`）、格式/UI/i18n/生产构建与 `pnpm release:check`，不得以单项通过代替完整发布检查。

## 2. jsdom 大列表测试超时定界

- 大列表交互集成测试按平台与实际渲染/导航工作量单独定界，同组等规模用例保持一致：
  - **205 行固定页用例**：CI `30s`、本地 `5s`。
  - **跨 200 行分页的 205 封阅读组**：CI `30s`、本地 `15s`。
  - **双模式跨页往返和末封用例**：以 202 封邮件覆盖实际 200 行分页、跨页返回、连续导航和末封禁用，保留 CI `60s`、本地 `30s`。
- **依据与红线**：原七次导航用例在 Windows 共享 runner 曾达到 68.5 秒，使用足够覆盖行为的最小边界数据。CI 超时先核对失败日志与断言，**禁止通过自动重试或全局延长超时掩盖业务回归**；单元测试断言与真实原生验收分别保留。

## 3. 真实收发测试授权范围（用户明确授权）

- **唯一授权邮箱对**：仅允许使用当前已登录的**腾讯企业邮箱**与**QQ 邮箱**相互发送测试邮件。发送前须核实发件账号与完整地址；若账号变动或无法确认，先向用户重新确认范围。
- **严格收件人限制**：收件人、抄送、密送只能包含这两个已授权邮箱，**严禁向任何其他地址发送或转发**（Gmail 已登录不扩大发信授权，向其他地址发信须另获用户明确授权）。测试邮件统一使用明确的“雁信联调”主题与无敏感数据内容，不沿用其他邮件的收件人列表。
- **验收与现场还原**：使用真实开发预览验收收发，分别记录 SMTP 接受、实际收取、正文与回复链结果；重建后补收不得记作 `IDLE` 延迟验收通过。测试临时修改的签名或设置须记录并在验收后恢复；真实存档迁移、邮件移动或永久删除不得作为无关测试顺手执行。

## 4. 关键原生与实机验收原则

- **原生能力不以浏览器/DOM 测试替代**：
  - 邮件正文安全外链（禁用脚本 `iframe`）：须实测原生点击唤起系统浏览器或写信窗口。
  - 单封邮件打印：须实测系统打印面板长正文分页与语言（`Info.plist` 声明简体中文），参数探针或浏览器 PDF 不替代原生长正文分页。
  - 双语翻译隐藏恢复：须在真实 WebKit 中核对 CSSOM 延迟同步，不只依赖 jsdom。
  - 实时收件（`IDLE`）：须以实际 `IDLE` 主动通知触发为验收依据，不得以缩短轮询、分钟级只读复核或重启补收替代。
  - 弹层层级：须核对实际视觉覆盖，DOM 存在或可点击不证明未被遮挡。
  - Windows 托盘与顶栏：实测自定义三键点击、最小化隐藏及 UIA/MSAA 真实托盘点击恢复（详见 [docs/WINDOWS.md](../WINDOWS.md#平台工程约束)）。
  - 凭据与升级：必须核对升级后实际可读取凭据，不能只凭代码签名验证通过宣称升级验收完成。

## 5. 版本核对与正式发布流水线

- **四处版本同步与暂存核对**：发版须同步 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 与 `src-tauri/tauri.conf.json` 的版本（若涉及依赖变更同步更新 `pnpm-lock.yaml`）并补充 `docs/releases/v<版本>.md`。提交前通过 Git 暂存对象核对四处版本，创建标签前再次从固定提交读取核对（工作树的 `release:check` 不能代替提交对象核对）；必须使用新标签，严禁改写已发布版本的标签或产物。
- **九资源草稿重建与串行保护**：正式发布使用组织仓库流水线收齐完整九资源（macOS Apple Silicon / Intel 各自 DMG、更新归档、签名，Windows NSIS EXE 与签名，以及三平台 `latest.json`）；沿用既有 Tauri 更新公钥与匹配私钥，无迁移方案不得换密钥。重建未发布草稿须同步固定源码提交与发布说明，同版本已有标签必须解析到本次源码（否则换新版本，不自动移动标签）。发布任务统一串行，上传前后重核草稿身份；网络/权限/查询失败不得当作版本不存在，正式公开前仍须独立核验全部产物。
- **发布说明一致性与更新中心**：发布说明在源码、`latest.json` 更新清单与 GitHub Release 中保留同一原文（含末尾换行）；生成/消费集成测试使用真实清单生成入口，不以手写近似清单漏掉格式差异。更新中心展示当前版本至目标版本之间所有适用已发布版本的完整说明与实际版本数（按语义版本筛选、去重、倒序，不以 patch 差值猜数量，不把分页失败或缺失目标当完整历史；失败可展示标注目标说明并重试，正文继续净化，桌面外链走系统入口）。
- **按更新条目署名**：由社区反馈促成的改动，在对应条目末尾写反馈者的 GitHub 用户名 `@username`。有公开 Issue 时可在用户名之前附上编号链接。准备 `docs/releases/v<版本>.md` 时，从 `UNRELEASED.md` 带入对应条目的署名，核对 `latest.json` 和应用更新弹窗中的用户名仍跟在该条后面。关闭 Issue 时简短回复处理结果和预计随哪个版本提供，版本未定时写「将在后续版本提供」。
- **Homebrew 自动分发校验**：正式 Release 审计公开为 latest 后，`homebrew.yml` 下载并校验双架构 DMG 并仅更新主仓库 `Casks/anser.rb`；临时 runner 仅显式信任 `ansermail/tap/anser` 单个配方再跑 `brew style / audit / fetch`（不关闭 Tap Trust 或扩大信任范围）；草稿/预发布/非 latest 不分发，重复执行无变化不提交；详见 [docs/HOMEBREW.md](../HOMEBREW.md)。
- **发布后核验与官网时序**：公开后核对匿名下载与标准更新端点返回 HTTP 200；确认安装器公开后再部署新版 Pages 官网并核对线上三端链接。明确分别记录应用代码签名、Tauri 更新归档签名与实际原位升级结果，并按无付费证书方式说明 macOS 首次打开限制。
- **旧个人仓库客户端迁移提醒**：早期旧客户端仍可能内置个人仓库更新地址；仓库克隆不会自动重定向，删除个人旧仓库前须确保旧客户端已完成迁移或安装组织版，不能把新仓库发布当作旧客户端已迁移。
